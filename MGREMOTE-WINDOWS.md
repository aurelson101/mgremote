# MGRemote Windows fork

Created 2026-10-29 from mRemoteNG `v1.78.2-dev`, commit `25ef453aaf18f292478dd41e5bb26798ff504312`.
Local branch: `mgremote/windows-security`; remote `upstream` is read-only by convention. No hosted fork or publication was created. GPL-2.0 and original notices remain applicable.

## Implemented

- Windows only: preserve the upstream .NET 10 Windows desktop project, x64 and ARM64 targets. No Linux/macOS application port.
- Separate fork identity: `MGRemote.exe`, `%APPDATA%\MGRemote` settings/connections, and a dedicated single-instance mutex. The upstream application is not automatically migrated or uninstalled.
- RDP: new profiles require server authentication. Imported profiles with NoAuth, warning-only authentication or disabled CredSSP are refused with a corrective message. Failure to set authentication aborts initialization. Use a trusted certificate matching the server FQDN; do not bypass errors. Server policy must also require NLA. RDP client patches remain the responsibility of Windows Update.
- SSH: new profiles default to the Windows OpenSSH terminal. The executable is resolved only from the Windows system directory. Explicit host-key checking, agent forwarding disabled, local commands disabled and compression disabled. Invalid host/user/port input is rejected. Algorithm availability depends on the installed, maintained OpenSSH client; no bespoke cryptography is introduced.
- SSHv1, Telnet and rlogin are refused in the protocol factory. PuTTY SSH also enforces SSHv2, disables agent forwarding and runs in batch mode: verify/cache the host key independently first, and use an agent or vault credentials (interactive password/passphrase prompts are unavailable in this backend). Additional PuTTY options are restricted to identity files and tunnels; arbitrary proxy commands, host-key overrides and plaintext password options are refused. VNC, raw sockets and HTTP remain available and are **not** covered by an assurance of encrypted transport.
- Vault-derived PuTTY keys: owner-only Windows ACL established before writing key material, an exclusive session lease, removal on close, and cleanup of abandoned sessions older than one day on the next key creation. An application crash may leave an owner-protected file until that cleanup. Deletion is not guaranteed physical erasure on an SSD. Local administrators and compromise of the current account remain outside this protection.
- Passwords and assigned credentials are unchecked when opening the export dialog. A user may explicitly select them; exported files still need appropriate handling.
- Automatic installation from upstream is blocked so an original mRemoteNG installer cannot replace this fork. No dedicated signed update channel exists yet.
- Existing upstream features retained: external vault integrations, DPAPI settings-key support, RDP Gateway/RCG code, environment tab colours and display scaling. These features have not been independently validated end to end.
- Tools > SSH keys and profiles: native Windows dialog for OpenSSH profiles, private-key selection, SSH certificates, ports and jump-host aliases. Key generation invokes the Windows `ssh-keygen.exe` directly in an interactive console; no passphrase is collected by the application and no PowerShell execution-policy change is needed. FIDO2 support is conditional on the installed client/token. Existing key files and profiles are never overwritten. Config backups preserve original bytes; invalid UTF-16/32 configs are refused unchanged.

## SSH keys, certificates and bastions

Run `Tools/Configure-MGRemoteSsh.ps1` explicitly; no real keys or user SSH profiles were changed during development.

```powershell
# Create the folder yourself if it does not already exist.
New-Item -ItemType Directory -Path "$env:USERPROFILE\.ssh" -Force
# Passphrase is entered directly in ssh-keygen, never in a script argument.
.\Tools\Configure-MGRemoteSsh.ps1 -Action GenerateKey -IdentityFile "$env:USERPROFILE\.ssh\mgremote_admin"
.\Tools\Configure-MGRemoteSsh.ps1 -Action Profile -Alias linux-prod -Hostname server.example.com -Username admin -IdentityFile "$env:USERPROFILE\.ssh\mgremote_admin"
# Optional: -CertificateFile <absolute SSH certificate path> -JumpHost <configured SSH alias>
# Optional hardware key: -Action GenerateKey -KeyType ed25519-sk (client/token support required).
```

In MGRemote select SSH2 / WindowsTerminal, use the generated alias as hostname, leave username empty, and set the configured port. OpenSSH reads the profile from the user's config. Verify first-use fingerprints independently. The helper creates a separate profile, refuses overwrites and backs up existing SSH config before adding an exact Include. Restore that backup and remove only the newly created profile to undo it. Existing PuTTY profiles retain their backend and separate host-key cache; their new batch policy refuses unknown or changed keys. Native OpenSSH prompts for credentials/uses its agent; it does not inject passwords or keys from the application's vault.

## Validation and build

`pwsh -NoProfile -File .\Tools\Test-MGRemoteSecurity.ps1` compiles and executes the new policy/key helpers and checks their integration points. It is not a complete application build or a live protocol test.

Validation on 2026-10-29: **61 targeted checks passed** in PowerShell 7, including compilation of all three new C# security/profile helpers, real Windows key ACL/lease cleanup, concurrent disposal, hostile option rejection and synthetic SSH profile creation/backup/overwrite rejection. The native profile tests also cover IPv6, bastions, incompatible PPK keys, path traversal and preserving existing config on encoding errors. Only synthetic test data was used and the test profile directory was removed. The complete x64 application build and self-contained publication succeeded using Visual Studio Build Tools 18.11.2 and .NET SDK 10.0.403, installed from the hash-verified Microsoft package via WinGet. Upstream compiler warnings remain; no live RDP/SSH authentication was performed.

`pwsh -NoProfile -File .\Tools\Build-MGRemote.ps1 -Publish` builds using Visual Studio MSBuild, inventories resolved dependencies and creates a fresh self-contained Windows payload under `artifacts/publish`. End users of this payload do not need to install the .NET runtime separately. Building requires the Visual Studio desktop build workload and .NET 10 SDK.

`Tools/Sign-MGRemoteRelease.ps1 -CertificateThumbprint <thumbprint>` signs the main executable and the application's own compiled DLLs using an existing Windows-store code-signing certificate and checks each timestamp and signer. It refuses self-signed release certificates and does not replace third-party publisher signatures. No signing certificate was supplied or generated.

## MSI packaging

Version 0.1.10 adds RDP Clipboard and Files settings from the connection context menu and New Connection. New RDP connections enable text/image clipboard sharing; existing imported connections retain their policy until explicitly edited. Custom/local drive modes now enable the drive-redirection channel, and clipboard setup is independent of drive errors. File mode may enable the channel with no whole drives selected; selecting a drive explicitly exposes that drive via tsclient. Reconnect after changes. Server/client policy remains authoritative; no registry/GPO bypass or remote rdpclip restart is performed. Large clipboard file copies have Windows limitations; use redirected drives for large files. See [Microsoft clipboard redirection](https://learn.microsoft.com/en-us/azure/virtual-desktop/redirection-configure-clipboard) and [large-file transfer](https://learn.microsoft.com/en-us/troubleshoot/windows-server/remote/copying-2-gb-file-by-clipboard-redirection-fails).

SSH text consoles now offer Copy/Paste context actions and Ctrl+Shift+C / Ctrl+Shift+V; pasting only fills the input and never executes it automatically. Shift+Enter adds a line, Enter sends. Incoming output preserves an active copy selection. Files/directory transfers use the explicit SSH Transfer action from the connection or session-tab menu: Windows OpenSSH scp 9+ in its default SFTP mode, optional identity/profile/agent, native-console password/passphrase entry and the configured bastion route. Upload/download and recursive directories are supported. Local file clipboard/drop input selects a source without starting transfer. Uploads may replace same-name remote files; downloads create a new local subfolder. Local links/junctions are rejected during upload validation. Cancellation preserves partial files and closes the owned transfer process/job and tunnel. The legacy password-only transfer plugin is no longer used by the session-tab action. No live server clipboard or authenticated file transfer has been validated here; those require a controlled pilot.

Version 0.1.9 adds an optional private-key picker directly to the SSH properties grid; clearing it restores the ordinary OpenSSH/agent/password flow. It edits the existing SSHOptions identity option without storing key contents or adding an XML attribute. PEM/OpenSSH and PuTTY PPK keys are validated for the selected backend. New Connection exposes an optional SSH bastion selector for RDP/SSH, and VNC creation requires an SSH tunnel by default. Configure the bastion as a separate SSH2 connection with its own optional key, then select it in the destination's Tunnel SSH field; destination and bastion keys/users remain independent.

Windows OpenSSH now supports that field through an owned native-console TCP forward bound only to 127.0.0.1, with ExitOnForwardFailure, asynchronous readiness/timeout/cancellation and a Windows kill-on-close job. Failure, closing the target session or exiting/crashing MGRemote closes its owned tunnel process. The native SSH console action also honors the selected tunnel. SSH profile aliases are resolved locally through ssh -G, and target host-key checking retains the real destination/port rather than trusting localhost. Duplicate bastion names and nested model tunnels are rejected explicitly. Existing PuTTY tunnels remain supported. RDP NLA and server-certificate authentication remain required: an RDP certificate/name mismatch through a loopback tunnel is not bypassed and needs a real environment pilot; VNC and SSH authentication also require live validation. Offline tests exercise the real client's arguments, optional-key grid editing and an owned loopback relay fixture's readiness, byte transfer, timeout, cancellation and process cleanup, not a real authenticated SSH tunnel.

Version 0.1.8 recovers off-screen/oversized windows to the monitor working area (including negative coordinates and taskbars), moves floating panels safely and marshals display-change notifications onto the UI thread. Monitor menus validate disconnected targets and show resolution. RDP fullscreen/smart-size resolution uses the session control's monitor rather than the main window's monitor. The connection dialog accepts an optional local OpenSSH/PEM private key; its existing serialized SSHOptions field carries a validated -i option to Windows OpenSSH. Private-key format markers and Windows ACLs are checked without changing the existing key; public keys and PPK files are rejected for OpenSSH. Passphrases remain handled by OpenSSH/ssh-agent. Creating a profile from the connection dialog transfers its alias and port back to the dialog. Terminal controls are managed children, avoid the former blocking handle wait and release their own process on close/failure.

AnyDesk is optional through Tools or a connection's context menu: it opens an already installed standard/custom client externally with one validated ID/alias argument, no shell, no injected password and no automatic installation. AnyDesk licensing, remote consent and authentication remain the responsibility of the external client. See [AnyDesk Windows CLI](https://support.anydesk.com/command-line-interface-for-windows) and [Microsoft Windows OpenSSH key authentication](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement). Targeted validation includes synthetic monitor geometry, real Windows ssh -G argument parsing, decrypting a synthetic encrypted Ed25519 key, ACL/input rejection, an owned loopback terminal process's cleanup and invalid AnyDesk UI input. These checks do not replace physical mixed-DPI/hot-plug testing or real RDP/SSH/AnyDesk authentication; no broad bug/security audit was performed.

For an encrypted SSH identity, use the SSH profiles dialog's explicit Load into ssh-agent action (the agent service must already be running), or right-click the SSH connection and select SSH — console Windows. These actions open the trusted Windows client in a native console for passphrase/password entry; MGRemote does not capture those secrets. No Windows service is changed automatically. The SSH/local-terminal backend no longer uses ConsoleControl after reproducing an exit callback into a disposed control. Its replacement text console bounds queued output and scrollback, reads streams asynchronously and cancels readers/terminates only its owned process tree on close. It is not a full ConPTY emulator; interactive authentication and full terminal applications should use the native-console path pending a dedicated ConPTY replacement. The dependency remains for the separate legacy PowerShell/WSL backends; migrating and testing those backends is still required.

### Install, upgrade and uninstall

An elevated deployment context is needed for the per-machine MSI; `/qn` does not bypass administrator requirements. Close MGRemote before maintenance. Use the exact MSI filename downloaded for that version:

```powershell
# Interactive install; rerun the installed package for repair/remove choices.
msiexec.exe /i "MGRemote-0.1.2-win-x64-preview.msi"
# Silent install OR upgrade from a lower MGRemote version, keeping user data.
msiexec.exe /i "MGRemote-0.1.2-win-x64-preview.msi" /qn /norestart
# Silent uninstall, keeping user data.
msiexec.exe /x "MGRemote-0.1.2-win-x64-preview.msi" /qn /norestart
# Explicit, irreversible deletion of the executing user's MGRemote data as well.
msiexec.exe /x "MGRemote-0.1.2-win-x64-preview.msi" /qn /norestart PURGEUSERDATA=1
```

A higher three-part MSI version triggers a major upgrade; rebuilding the same version is not an upgrade strategy. Windows Installer return codes 0 and 3010 mean success (3010 indicates a reboot is required). Other codes must be investigated.

The maintenance wizard offers an unchecked option to remove the current user's MGRemote data when uninstalling. It deletes only MGRemote's roaming/local data, application-specific user.config folders, generated `.ssh/mgremote` profiles, their exact Include lines and MGRemote-generated config backups. Personal SSH private keys, other SSH profiles and other applications are preserved. Upgrades and repairs never run this cleanup, even if PURGEUSERDATA is set. Cleanup refuses redirected/reparse-point profiles, running MGRemote processes, and SYSTEM/service-account execution; run it as the affected user rather than guessing or deleting other users' profiles. Deletion is irreversible and not guaranteed physical erasure. Windows Installer, event logs, security telemetry and Windows-managed caches are retained; the package does not promise forensic trace removal.

Version 0.1.1 reads `CurrentBuildNumber` from the 64-bit Windows registry for its OS prerequisite instead of relying on the Windows Installer `WindowsBuild` compatibility property. `Tools/Test-MGRemoteInstaller.ps1` runs only AppSearch and condition evaluation in a read-only MSI session: it checks the real detected build, a simulated compatibility build of 9600, supported/unsupported OS boundaries and maintenance access. It does not install the application.

Optional `-CertificateThumbprint <thumbprint>` signs the executable, application DLLs and MSI using an existing Windows-store Code Signing certificate. An unsigned build remains a **preview**, and signing does not replace clean-machine install/uninstall or live protocol tests. Signing can improve publisher identification/reputation but cannot guarantee acceptance by SmartScreen or every antivirus. There is no code-signing certificate available for this build. No automatic update channel is enabled. Do not redistribute a binary without its matching source ZIP and manifest.
